# 信息收件箱

保存业务过程中的零碎信息，例如构建要求、bugfix 关联、设计文档入口或与同事确认的约定。目标是用户一句“记一下”就能留下线索，之后直接让 Agent 找回。

## 捕获方式

1. 仅在用户发起记录时写入。使用 [模板](TEMPLATE.md)，保存到 `inbox/YYYY-MM/<id-slug>.md`；`YYYY-MM` 使用记录当时的本地月份。
2. 保留用户提供的原话或原始内容，并把 Agent 提取的摘要单独写明。从上下文提取日期、来源、涉及的仓库／分支／特性，不编造缺失值。
3. 同步 [备忘索引](index.md)，列出日期、标题、适用范围和链接。用户无需事先分类或填写完整字段。
4. 记录是收件箱捕获，不表示事实已验证、要求仍然有效，也不表示已批准实施。

相同信息已有记录时，先判断是补充同一条，还是不同时间、不同分支的新消息。补充时保留原文及日期；存在冲突时并列保留来源与时间，不能无依据覆盖。未经用户发起，不批量整理、归档、改状态或转成知识。

## 元数据与检索

页面顶部使用简单的单行 frontmatter，字段见模板。`id` 以 `M-` 开头且全库唯一，改名或移动时保留。日期使用 `YYYY-MM-DD`。

| 字段 | 含义 |
|---|---|
| `id` / `title` | 稳定标识与可搜索标题 |
| `recorded` | 写入日期；消息发生日期另记正文，未知则写待确认 |
| `scope` | 已知的分支、版本、特性等适用范围；未知写待确认 |
| `status` | 默认 `recorded`；有依据且用户发起维护后可改为 `superseded` 或 `resolved` |

`recorded` 只表示已记录，`superseded` 表示有明确的后续信息替代，`resolved` 表示对应事项已确认结束；状态不是事实核查等级。标记替代时关联后续记录并保留历史。

检索同时查标题、原文、摘要、版本、标识和同义问法。返回记录时带日期、适用范围和来源。用户询问当前做法时，结合目标代码仓／版本进行只读核查；无法读取来源、目标版本不清或证据冲突时明确说明。核查结果留在回答中，写回仍须用户发起。

备忘中形成了可复用原理时，可以提醒用户是否需要整理为业务知识；收到指示后才整合，并保留来源关联。详见 [操作流程](../docs/workflows.md)。
