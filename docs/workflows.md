# 操作流程

执行边界统一见 [AGENTS.md](../AGENTS.md)。本文件说明在该边界内如何完成任务；目录字段分别见 [知识规范](../knowledge/README.md) 与 [备忘规范](../inbox/README.md)。

## 识别用户意图

| 输入 | 动作 | 持久化变化 |
|---|---|---|
| 普通提问、找回链接、核查旧说法 | 检索与回答，必要时只读查证 | 无 |
| AI 提示“是否需要记录”，用户未明确要求 | 等待用户决定 | 无 |
| 用户要求记录业务理解 | 查重、整理知识、合理挂载 | 本任务正文、索引及维护记录 |
| 用户要求记下通知或链接 | 轻量保存为备忘 | 本任务备忘、索引及维护记录 |
| 用户要求整理收件箱、合并主题或纠错 | 按指定范围维护，保留历史依据 | 范围内必要文件 |

“可以提醒我”是提醒授权；“记录一下”是本次写入授权。授权不延伸为之后每次聊天的自动沉淀。只有分类会实质改变用户意图、且无法从上下文判断时，才作简短澄清。

## 记录业务知识

1. **确认上下文**：利用现有对话和代码资料，确定要保留的问题与结论。不会因为用户要求记录就凭空补齐整个领域。
2. **检索已有内容**：检查问题入口、知识体系、别名和正文。相关主题已存在则局部更新；不是为每次问答新建一个文件。
3. **核对依据**：区分通用原理与公司实现；对实现记录仓库、版本、路径／符号及实际核查范围。依据不足时标记草稿或待核实，保留用户的已知信息，不冒充验证。
4. **选择挂载**：优先按业务领域 → 主题组织；选择一个主要归属，其他概念通过相关知识链接连接。已有结构不适合时，作本次主题需要的最小调整，大范围重构留待用户发起。
5. **整理正文**：从 [模板](../knowledge/TEMPLATE.md) 取需要的结构，讲清核心结论、关键逻辑、公司实现／适用条件、常见问题及来源。模板是提示，不要求每篇同样长。保留重要历史条件，避免用新结论无痕覆盖旧实验观察。
6. **同步入口**：更新 [知识体系](../knowledge/index.md) 的对应节点，在 [问题入口](../questions.md) 添加或修订自然问法及别名，链接到对应正文或小节；索引不复制答案。跨主题关联按实际影响更新。
7. **检查与同步**：按下文完成结构检查、维护记录和 Git 同步。

## 轻量记录信息备忘

1. 保留用户提供的原话或原消息内容，独立标出从上下文提取的线索。原消息没有的事实不能由 Agent 补成确定结论。
2. 从 [模板](../inbox/TEMPLATE.md) 创建 `inbox/YYYY-MM/<id-slug>.md`；月份按记录日期。日期、标题、分支／特性、来源等由 Agent 提取；无法确定的来源和适用范围明确写待确认。
3. 区分**记录日期**与**原消息日期**，不把入库时间当作通知发生或生效时间。同一消息重复记录优先补充已有条目；确有后续信息则关联原条目，不覆盖原话。
4. 更新 [收件箱索引](../inbox/index.md)，保留标题、日期、适用范围、别名等检索线索。知识关联可以指向已有主题，不因此另行创建知识正文。
5. `recorded` 表示消息已保存，不保证内容当前仍适用。用户要求维护后，才能补充状态或关联后续消息；历史原话继续保留。
6. 用户另行发起整理或知识沉淀时，提炼有依据的内容并链接回原备忘；不做定期自主清箱，也不为所有备忘强制建立业务分类。

## 查询与当前情况核查

1. **找回记录**：明确用户的问题、目标分支／版本和需要的信息。先读问题入口及相关索引，再检索正文；标题没命中时搜索别名、特性、仓库、分支和原话关键字。读到原始依据再下结论。
2. **判断需要什么核查**：找一个历史文档链接可以直接返回来源；询问“现在怎么构建”“当前实现是否如此”等时，需核对当前情况。纯概念问题无需无关全仓扫描。
3. **定位版本**：通过每人自己的路径映射定位业务仓。只读检查其 ref／commit 和相关工作区差异；优先使用用户指定版本。分支、提交或文档版本不明确且会改变结论时，说明缺口或澄清。
4. **查证相关依据**：比较记录中的条件与当前代码／文档／Git 历史。发现已合入、改写或被替代时，给出能支撑该判断的实际依据。不能仅凭提交标题相似就断言修复已包含。
5. **输出答案**：先回答问题，再标明当前目标和历史范围，链接依据；明确未核实部分。核查的是未提交工作区时，也须指出。
6. **保持查询只读**：不修改知识内容、状态、索引或维护记录，不产生内容提交。可提示用户是否需要更新该条；取得新的维护指示后再执行写入流程。

来源无法访问时可以回答“记录显示……，本次未核实当前情况”。不得以历史备忘替代当前已确认结论。业务代码的核查只读限制见 [执行规则](../AGENTS.md)。

## 检查、维护记录与 Git 同步

本节只用于用户发起的写入任务。

1. 写入前检查本地状态与已配置的共享分支，确保基于最新可用版本；只无损同步，不覆盖他人变更。未提交内容和远端变动冲突时先保留各方有效内容，再处理本任务。
2. 在 [CHANGELOG.md](../CHANGELOG.md) 记录日期、操作类型、涉及文件、依据、实际检查结果与未解决问题；不复制正文。
3. 运行结构检查和 `git diff --check`。机制／脚本修改还须运行全部自动测试，审阅受影响行为场景；普通知识修改重点核查来源、适用范围、挂载和关联。
4. 结构错误修复后再提交；提醒按实际情况判断，不能为消除提示制造空主题或无意义链接。
5. 仅暂存本任务文件，提交到当前约定的共享分支并推送已配置 remote。若远端前进，重新读取相关内容并合并验证；不强推。没有配置 remote、权限不足或冲突尚未解决时，清楚报告本地成果和未共享状态。
6. 回复简要列出知识／备忘位置、入口变化、验证结果与同步状态。不要把“脚本通过”写成“技术事实或所有 Agent 行为均正确”。

克隆后先按 [接入说明](setup.md) 确认共享 remote。读取共享更新属于获取已有内容，仍需保护本地改动；不得借查询之名创建或整理新内容。
