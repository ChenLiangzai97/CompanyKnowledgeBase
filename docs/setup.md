# 接入与共享

这个仓库保存 Markdown 内容、导航和 Agent 规则。每个人通过自己的 Agent 读取和使用，不需要常驻服务。

## 1. 准备共享仓库

当前 GitHub 仓库是通用框架。公司业务内容应存放在公司允许的位置；可以将框架导入公司 Git 服务，再让同事克隆同一个共享仓库。

仅查看通用框架可运行：

```bash
git clone https://github.com/ChenLiangzai97/CompanyKnowledgeBase.git
cd CompanyKnowledgeBase
```

实际使用公司共享仓库时，将克隆地址替换为公司批准的地址。阅读者具备读取权限；维护者具备所需写入权限。写入、检查和同步流程以 [操作流程](workflows.md) 为准。

## 2. 配置自己的代码仓映射

知识库与业务代码仓独立，知识库中不保存业务代码副本。每个人的目录可以不同。在知识库根目录创建被 Git 忽略的 `workspace.local.md`，或在当前会话直接提供路径：

```markdown
# 本机仓库映射

| 仓库标识 | 本地路径 | 默认参考分支 |
|---|---|---|
| training-framework | /your/local/training-framework | 待确认 |
```

映射只帮助 Agent 找到代码。实际核查时检查当前分支、commit 和工作区改动，明确目标版本；默认分支字段不证明本地检出的就是该分支。查询不授权切换分支、拉取改变工作区的更新或修改业务代码。

共享正文中使用“仓库标识＋版本／commit＋仓内相对路径＋符号名”作为代码依据，能提供稳定的公司代码链接时一并提供。保留未提交改动对核查的影响，不能把它当成可由同事重现的提交版本。无法读取代码时返回已知内容及核查限制。

## 3. 让 Agent 显式读取规范

复制 [接入提示](../prompts/bootstrap.md)，替换知识库和代码仓路径后发给 Agent。Agent 至少先读 [仓库入口](../README.md)、[执行规范](../AGENTS.md) 与 [全库导航](../index.md)，再按任务读取局部规范。

如果希望在业务代码仓长期保留入口，由用户发起修改，在该仓现有 Agent 规范或说明中加入知识库位置及读取要求。不同工具如何加载规则需按实际工具配置确认；放置文件本身不保证所有 Agent 都会自动读取。指向知识库的入口应引用统一规则，避免另复制一套内容。

## 4. 日常使用

| 用户表达 | 预期行为 |
|---|---|
| “这个机制是什么？” | 检索与回答，按需只读核查，不改库 |
| “把刚才讨论的知识记录下来” | 检索已有主题、整理正文、更新相关导航并检查 |
| “记一下，这个分支构建需要带某个修复” | 轻量保存备忘及上下文线索 |
| “某个特性的设计文档在哪里？” | 从索引和备忘原文中找回来源，说明记录日期和范围 |
| “整理这些备忘” | 仅在这次指示的范围内整理，保留来源与必要历史 |

维护前获取最新共享版本并检查本地状态；存在未提交改动或远端变动时按流程处理，不能覆盖他人内容或强制推送。普通查询不应暗中触发知识整理和 Git 提交。

## 5. 检查

在仓库根目录运行：

```bash
python3 scripts/check_knowledge.py
python3 -m unittest discover -s tests -p 'test_*.py' -v
git diff --check
```

结构检查只验证它实际实现的结构规则，不证明技术结论正确或信息仍然有效。完整限制和验收范围见 [设计说明](../DESIGN.md)。
