# 业务知识

这里维护经过整理的业务理解：原理、公司实现、适用条件、依据，以及尚未确认的问题。以 [知识体系](index.md) 查看领域与主题，以 [问题入口](../questions.md) 从日常问法定位正文。

## 组织与挂载

- 按业务领域 → 主题组织，文件建议放在 `knowledge/<领域>/<主题>.md`。先检索已有标题、别名、问题和正文，优先增量更新已有主题。
- 同一主题维护一份正文。跨领域内容选择主要归属，在其他入口放链接；问题入口链接到对应小节，避免为每种问法复制答案。
- 体系随已经记录的内容生长。没有实际内容时不批量创建空页面，不为完善目录自行补课或扩写。
- 新增或实质更新后，同步 [知识体系](index.md) 和相关 [问题入口](../questions.md)。只建立有意义的前置知识、上下游与相关主题链接。

## 内容与依据

从 [模板](TEMPLATE.md) 起步，按主题删去不适用的小节。先给出可用结论，再解释关键过程；必要时用表格或 Mermaid 图帮助理解。涉及公式时解释每个符号。

正文应能区分：

| 内容 | 记录要求 |
|---|---|
| 通用原理 | 写清概念与边界，关联实际读取的来源 |
| 公司实现 | 写清代码仓标识、分支或版本、commit、相对路径和符号；只填实际取得的信息 |
| 当前理解 | 标明哪些是来源陈述、哪些是分析推断；没有依据的设计动机标为待确认 |
| 历史情况 | 保留当时版本与条件，说明后续变化，不把旧结论改成“当时就知道” |

绝对本地路径可以作为本次定位线索，但不能成为共享内容中唯一的代码依据。不同人的本地路径由 [接入配置](../docs/setup.md) 映射。

## 元数据与状态

页面顶部使用简单的单行 frontmatter，字段见模板。`id` 以 `K-` 开头且全库唯一；移动或改名保留 ID。日期使用 `YYYY-MM-DD`。

| 字段 | 含义 |
|---|---|
| `id` / `title` | 稳定标识与可搜索标题 |
| `domain` | 业务领域及主题归属 |
| `created` / `updated` | 页面创建日期与内容修改日期；修改日期不代表技术核查日期 |
| `status` | `draft`、`verified` 或 `needs-review` |

新整理内容默认 `draft`。`verified` 要有明确的核查日期、范围、版本和依据；仅仅生成了笔记、通过结构检查或讨论过，不构成验证。发现未解决冲突时用 `needs-review`，正文保留具体疑点。来源不足写“待确认”，不要求用户补齐表单后才能捕获。

记录、合并、重组、状态变更均须属于用户已发起的任务。普通查询可以核查现状，但不修改页面。完整边界与执行流程见 [Agent 规范](../AGENTS.md) 和 [操作流程](../docs/workflows.md)。
